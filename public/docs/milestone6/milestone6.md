There is currently no automatic cleanup of stored file blobs when evidence metadata is removed; retention and garbage-collection must be implemented at the storage layer or as a background job.

#### Norms Extraction Service
- **Knowledge Base:**
  - **Data:** Extracted normative content text. *(Note: This service does not directly process personal data, focusing on the processing of normative documents and storage in MongoDB).*

### 1.2. Security Measures and Access Controls (DPIA-UA)

#### Delegation of Authentication
- We do not store passwords locally in our databases. Identity management is fully delegated to an external provider (Keycloak), using JWT token validation with RS256 encryption (JWKS).

#### Strict Access Control (RBAC)
- Permission checks are implemented on all critical endpoints, restricting access based on specific roles (`practitioner`, `specialist`, `sys_admin`, `org_admin`) and limiting data visibility to the organization ID (`org_id`).

#### Data Protection and Minimization
- **Asymmetric Encryption:** In the Norms Extraction Service, the LLM API key is encrypted client-side with an RSA public key and decrypted securely only on the server, avoiding credential exposure in transit.

- **Input Validation:** A strict allowlist for file types (MIME types), upload size limits (maximum 50MB), and text truncation before sending to the AI model are implemented.

#### Infrastructure Isolation
- **Network Isolation:** Use of dedicated Docker networks (bridge networks like `certibot-network` and `norms-network`) to segment and protect internal traffic between microservices and databases.
- **Abuse Prevention:** Rate limiting on critical endpoints to prevent denial-of-service attacks and resource exhaustion.

#### Infrastructure Protection Strategy (At Rest and In Transit)
- **Security in Transit (TLS with Nginx):** At the network level, we ensure data-in-transit security using a reverse proxy (Nginx) responsible for TLS termination (HTTPS). This architectural approach centralizes certificate management and removes cryptographic processing load from microservices (FastAPI).
- **Encryption At Rest:** At the application level, we have chosen not to implement column-level encryption in the databases (PostgreSQL/MongoDB) to avoid performance degradation and retain searchability. To satisfy Article 32 of the GDPR ("appropriate security based on risk"), mitigation in production is delegated to cloud infrastructure (e.g., enabling Transparent Data Encryption or using AWS EBS/RDS volumes), ensuring physical data protection without impacting the code.

### 1.4. Automated Decisions and "Human-in-the-Loop" (Article 22 of the GDPR)

#### Confirmed Implementations (What We Already Do)
- **Human Override Mechanism:** The system acts only as decision support. We have implemented routes (e.g., `PATCH /audits/{audit_id}/override`) that allow a human user to change the audit result, recording the reason (`override_reason`), the date, and who made the change (`overridden_by`).
- **Uncertainty Flagging:** The system automatically sets a `needs_human_review` flag on audit results whenever the AI shows uncertainty, forcing human review.

#### Risk Identification and Future Work (Gaps)
- **UX Message:** There is no clear UI message assuring users that compliance decisions are not made 100% automatically.
- **Mandatory Review Flow:** Currently, override is optional; the ideal flow should require human validation (a gatekeeper) before an audit is marked "closed."

### 1.5. AI Supply Chain and Data Sharing (GDPR and NIS2)

#### Confirmed Implementations (What We Already Do)
- **Security in Transport:** Access to the norms extraction API requires encrypted keys (RSA OAEP).
- **Input Validation:** Security mechanisms for evidence submission (size limits, text truncation, and strict MIME type allowlist) are implemented.

#### Risk Identification and Future Work (Gaps)
- **PII Sanitization (GDPR):** There is currently no scrubbing/redaction mechanism for personal data (e.g., names or emails in evidence documents) before sending text to external models (Google Gemini or Ollama). This will be a technical priority.

- **Vendor Training Opt-out:** It is necessary to ensure configuration flags on external APIs explicitly prohibit the use of our data (and our users') to train vendors' public models.

- **Vendor Controls (NIS2 / Article 28 GDPR):** Legally, the project will need explicit Data Processing Agreements (DPAs) with LLM vendors to guarantee supplier resilience and security.

### 1.6. Right to Erasure (Article 17 of the GDPR)

#### Confirmed Implementations (What We Already Do)
- **Cascade Deletion:** The system already has database rules for deleting conversations (`DELETE /conversations/{conversation_id}`). The architecture uses strict cascade rules (`cascade="all, delete-orphan"` in SQLAlchemy) ensuring that deleting a chat session permanently removes all associated messages from PostgreSQL.

### Risk Identification and Future Work (Gaps)
- **Lack of Proper Deletion Endpoints (Anonymization Approach):** Currently, the API does not have dedicated endpoints for deleting Organizations or Users. To address the Right to Erasure while preserving system integrity, the project will follow an **anonymization approach** rather than hard deletion:
    - **User Anonymization:** When a user is "deleted," their personal identifiable information (PII) will be scrubbed or randomized. This ensures that the **Organization's audit trail** (e.g., who validated which evidence) remains safe and intact without exposing the former user's identity.
    - **Organization Anonymization:** If an organization is removed, its data will be anonymized to keep the **compliance process history** safe for **Business Intelligence (BI)** and trend analysis, ensuring the project's data remains valuable without identifying the specific organization.
- **Orphaned Data Risk (Keycloak Synchronization):** Since Keycloak manages users, if a user is deleted in Keycloak, their records in our database (the `UserDB` table) remain ("orphans"). Mitigation will require a mechanism (e.g., Keycloak webhooks) to trigger the anonymization flow in PostgreSQL.
- **Legitimate Retention (Evidence and Audits):** Audit reports and evidence files belong to the Organization (the Data Controller), not the individual employee. This is a desired and legally defensible behavior fitting under legitimate interest and legal obligations, which can override an individual's right to erasure for the purpose of maintaining a permanent record of compliance.

### 1.7. Data Sharing and Subprocessors (Data Processing Agreements)

For Certibot to operate, we rely on external entities that process data. Under the GDPR, these entities are classified as "Subprocessors."

#### External Entities Identified (Subprocessors)
1. **Google Gemini API:** PDF processing and norms extraction (*Norms Extraction Service*). This is the project's only external subprocessor.

#### Local Infrastructure (Not Subprocessors)
- **Keycloak Identity Provider:** Management of user lifecycle, identities, and permissions. This service is **self-hosted locally**, ensuring no personal data is shared with external identity providers.
- **Ollama LLM:** Generation of audit responses. This service is **run locally**, ensuring that prompt data and audit context remain within the project's infrastructure.

#### Confirmed Implementations (What We Already Do)
- **Prevention at Source:** We minimize exposure risk by strictly limiting shared file types (MIME allowlist) and upload size limits.
- **Data Minimization:** We implement text truncation before sending data to the LLM to ensure only necessary context is processed.
- **Security in Transit:** We ensure the security of communications by using encryption (RSA OAEP for API keys) to protect access to the APIs during transmission.

#### Risk Identification and Future Work (Gaps for Production)
This risk analysis revealed crucial steps required for full GDPR compliance in a production environment:
- **PII Sanitization:** Implement a mechanism to scrub or redact personal data (PII) from evidence documents before they are sent to external LLMs.
- **Data Residency (EU Region Pinning):** Configure our calls to the Google Gemini API to enforce Data Residency in Europe, ensuring data is processed and stored exclusively in EU regions.
- **Legal Formalization (DPAs):** From a legal standpoint, formalize the entire workflow by establishing Data Processing Agreements (DPAs) with our external subcontractors.
- **Vendor Training Opt-out:** Ensure technical parameters are in place to explicitly prohibit external vendors from using our prompts or documents to train their public models.
- **Breach Notification:** Implement technical hooks or operational processes to rapidly notify responsible parties if the local infrastructure or external APIs suffer a security breach.

We reviewed the licenses of the project’s third-party dependencies to confirm that they provide a legally viable basis for commercialising the product. This assessment focuses on identifying restrictive licensing conditions (e.g., copyleft obligations), and ensuring that the project’s distribution and usage model remains compatible with those conditions.

The remaining **1/52** dependency is an **LGPL** case (**psycopg2-binary**). As currently used (via dynamic linking and without modification of the library source), this does not require the proprietary application code to be open-sourced. Nevertheless, the project still treats LGPL components as higher-sensitivity dependencies and applies stricter compliance checks.


In addition to software licensing, the **Ollama - llama 3.2** local LLM’s usage policy is treated as an operational constraint. The platform adopts a conservative stance that prohibits using the chatbot to:

- Process personal data of minors.
- Facilitate fraud or deceptive practices.
- Promote or enable violence.
- Support criminal activity.

### 2.2. Norm Licences

Unlike most software dependencies, compliance standards are typically copyrighted normative documents. As a result, the project treats the standard’s licensing conditions as a first-class constraint when ingesting, storing, and presenting normative content.

For **ISO/IEC 27001**, the licensing assumptions adopted for this project are:

- The standard text must not be translated or modified without explicit authorization.
- Copying excerpts (parts of the standard) is only acceptable when explicitly authorized by ISO/IEC and used within the permitted scope.

To remain compliant with these constraints, the project follows these practices:

- Avoid redistributing the full standard text in the product or repository.
- Prefer storing **structured, derived content** (e.g., clause identifiers, requirement objects, and internal notes) over storing verbatim paragraphs from the standard.
- When excerpts are necessary (e.g., for traceability), keep them minimal, access-controlled, and tied to the permitted use case.
- Maintain clear provenance by referencing clause identifiers and source metadata, rather than duplicating large portions of copyrighted material.

If CertiBot is deployed commercially, the handling of ISO/IEC standards should be validated against the applicable licensing terms and, where required, supported by formal authorization or commercial licensing agreements.

## 3. Sector-Specific Regulation

### 3.1. Domain Identification: The RegTech Sector
The CertiBot is positioned within the **RegTech (Regulatory Technology)** and **GGRC (Governance, Risk, and Compliance)** industry. It is a horizontal infrastructure designed to automate compliance processes across multiple domains, rather than being a tool restricted to a single niche.

#### Norm-Agnostic Philosophy
*   **Study Case vs. Product**: While we are currently using **ISO/IEC 27001:2022** as our functional prototype, the engine is entirely agnostic.
*   **Dynamic Data Model**: Our choice of **MongoDB** for normative requirements and **PostgreSQL** for evidence logs allows us to switch sectors (e.g., from IT to Healthcare or Finance) simply by uploading a new normative dataset. We provide the "pipes"; the client provides the "content."

---

### 3.2. Cross-Sector Mandatory Regulation: The EU AI Act
Since our core value proposition relies on Large Language Models (LLMs) to interpret legal and technical requirements, the **EU AI Act** is the most significant regulation impacting our development in 2026.

#### Human-in-the-loop (HITL) Integration
*   **The Legal Requirement**: European law mandates that AI systems used to assist in decision-making must have human oversight to prevent bias or automated errors.
*   **The CertiBot Solution**: This is the primary reason for our **Norms Review Service**. Every requirement extracted by our AI is flagged for **Expert Validation**. A human Norm Specialist must review and approve the data before it enters the production environment for clients.

#### Traceability and Hallucination Mitigation
*   **The Legal Requirement**: AI systems must be transparent about their sources and reach conclusions based on high-quality data.
*   **The CertiBot Solution**: We utilize a **Retrieval Augmented Generation (RAG)** architecture. This ensures the AI is "grounded" in the specific normative text stored in our database, directly preventing the AI from hallucinating or making up requirements that do not exist in the law.

---

### 3.3. Auditing Excellence: ISO 19011 Guidelines
Because the CertiBot is an audit-support tool, it must respect the international guidelines for auditing management systems.

#### Evidence-Based Decision Making
*   **Verification Orchestration**: Our system automates the mapping of evidence files to specific clauses. This fulfills the ISO 19011 requirement for an "evidence-based approach," ensuring that compliance status is never a guess but a result of verifiable documentation.
*   **Immutable Audit Trail**: We maintain a rigorous history of every expert validation and evidence update. This provides the transparency and accountability required for a professional audit to be legally and technically valid.

---

### 3.4. Scalability and Vertical Adaptability
By focusing on a RegTech infrastructure rather than a single-sector tool, we can justify our presence in any industry mentioned in the slide:

*   **IT Management**: We can easily ingest **ISO 20000** or **ITIL** frameworks.
*   **Healthcare**: The system can adapt to **ERS (Entidade Reguladora da Saúde)** regulations by simply loading clinical compliance modules.
*   **Finance**: We can support **PSD2** or **DORA** compliance by mapping payment and resilience directives into our extraction engine.

#### Conclusion: Compliance by Design
The CertiBot is built with a "Compliance by Design" mindset. By aligning with the **EU AI Act** for our intelligence and **ISO 19011** for our auditing logic, we ensure that our platform is legally viable and commercially trusted across the entire European market.

## 5. Technical Risks
### 5.1. Critical External Dependencies Risks

This section identifies external dependencies that are critical for CertiBot’s operation. Because these components are maintained and governed by third parties, they represent a non-trivial source of operational risk (e.g., pricing changes, policy restrictions, deprecations, and availability incidents). For each dependency, we describe the primary risk and the mitigation strategy adopted to reduce vendor lock-in and limit the blast radius of disruptive changes.

#### Gemini / Ollama / Gmail SMTP
- **Risk**: The platform relies on external model providers and email delivery (SMTP). Changes in pricing, usage policies, or service availability can directly affect core features (extraction, chatbot, inference, and email notifications).
- **Mitigation**: Maintain an adapter-based integration layer to enable rapid switching between model providers and transport implementations with minimal impact on the application code.

#### Keycloak-JS / @react-keycloak/web
- **Risk**: The authentication flow depends on a third-party wrapper around Keycloak. If the wrapper becomes unmaintained or lags behind breaking changes, it can block upgrades and introduce security or compatibility risks.
- **Mitigation**: Keep the authentication integration isolated behind a dedicated context/provider boundary so that replacing the wrapper (or changing the integration strategy) remains a localized change.

#### React & React-Router
- **Risk**: Major releases can introduce breaking changes that impact routing, rendering behaviour, and the overall frontend architecture.
- **Mitigation**: Apply strict version pinning and require automated test coverage before upgrades; plan manual refactors as part of controlled upgrade cycles.



### 5.2. Tech Debt and Brittle Components
#### General

##### Only unit tests
- **Problem**: The backend services have many unit tests to verify the logic of each component, but does not have integration tests for verifying the correct behaviour when connecting components together, which can cause brittle components.
- **Reason**: Integration was straightforward and didn't need much testing.
- **Solution**: Make integration tests for all interactions.

##### Incomplete/scattered documentation
- **Problem**: There is documentation in the endpoints themselves through openAPI decorators and in the `docs` repository, but the swagger documentation is not directly accessible in the dev environment and there is not a centralized place for the API documentation. There also exists other service-specific documentation outside the `docs` repository in a `docs` directory inside the service repo.
- **Reason**: The documentation was scattered because idk.
- **Solution**: Merge all service-specific documentation into the `docs` repo and add a global API documentation in the README for each service or in the same repo.

#### Compliance AI assistant service

##### Naive context window management in evidence
- **Problem**: The service uses a simple truncation mechanism on the concatenated evidence texts. Cutting off text arbitrarily can remove important info needed to prove compliance, directly changing the outcome of an audit based purely on which files were concatenated first.
- **Reason**: This is done in order to prevent exceeding the context window of the LLM or filling it up to a level that would damage performance.
- **Solution**: Split the evaluation into many requests for large evidence documents and merge the responses.

##### Evidence is stored directly on the file system
- **Problem**: The uploaded evidence files are stored directly in the file system inside the container, which introduces massive problems with horizontal scalability (multiple instances won't have access to the same documents), data syncing (restarting the containers destroys the evidence, while postgres still has the metadata) and IO blocking (the file storage operation is blocking, which can cause the blockage of the whole service with large uploads).
- **Reason**: To have a functional version of the feature working.
- **Solution**: The most direct solution involves introducing a local object storage service to allow for better and more centralized storage.

##### Ollama logic is handled directly through HTTP API
- **Problem**: While the interaction with the LLM is confined to the LLM adapter service, the logic inside of it makes direct use of the HTTP REST API that Ollama provides. This can cause problems if the API schema were to change.
- **Reason**: At the time of development, the team was not aware of the Ollama library for Python.
- **Solution**: Change all LLM interaction logic to use the Ollama library.

#### Norms extraction service

##### No feedback on background tasks
- **Problem**: The main operations that this service provides (extractions and translations) run in the background in threads because they are processes that take up a long time, but there is no possibility to see the progress of one of these tasks, or if they resulted in an error without directly looking at the logs in docker.
- **Reason**: Development speed (since this service mostly runs locally on the teams' computers, it was simpler to directly look at the logs to check out errors rather than making an additional system to handle it)
- **Solution**: Each task that runs in a separate thread is added to a service that tracks the state of that process. New endpoints can be created to check up on the state of each task without having direct access to the system.

##### Coupling with the main service
- **Problem**: As the extraction, review and translation processes are not meant to be running at all times, the norms extraction service was designed to be completely independent from regular use (system management and logic related to the businesses processes). But the endpoint for norm retrieval (meant for norm reviewers) is used in the chatbot and evidence pages, forcing the service to be a critical dependency for the overall function.
- **Reason**: This was done because the endpoint logic would be mirrored in two distinct services and changes made in one place would have to be mirrored in the other and because the naming of the endpoint made sense for the endpoint used by regular users.
- **Solution**: As the endpoint does not include complex system logic, the best course of action is to duplicate it on both services, changing the path on the norms extraction service to better match that environment.

#### Frontend

##### Manual Data Normalization
- **Problem**: The frontend uses deep ternary statements and nullish-coalescing chains to guess the shape of the backend data (checking for id, user_id, and userId). While this masks schema inconsistencies between backend services, it allows for unsanitized responses to reach the frontend (ones that the logic itself might not be checking against), which can cause silent data drops or invalid table rendering.
- **Reason**: 
- **Solution**: Introduce a validation library on the frontend to explicitly map and validate the expected schema upon receipt.

##### Client-Side Synthetic ID Construction
- **Problem**: The frontend generates unique identifiers for UI components by concatenating strings (e.g., ${normId}::${parentClauseId}). The ControlsTree relies on splitting this exact string to manage selection and expansion state. If the separator (::) ever appears in one of the concatenated components, the UI state management will completely break.
- **Reason**: 
- **Solution**: Shift the responsibility of generating hierarchical, unique node IDs to the backend database. The frontend should treat all IDs as opaque strings and not attempt to parse meaning or hierarchy from them.


## 6. Business Plan
### 6.1. SWOT Analysis

#### Strengths:
- **Human-in-the-loop QC**: Specialists review the norm model before it goes live and practitioners can override AI verdicts. This approach is benefitial to reduce the risk of misinformation.
- **Local LLMs for businesses' data**: Keeping compliance data off external servers is good for keeping the trust and maintaining the privacy of the businesses.
- **Accessible audit preparation**: Fills the gap for small businesses that can't afford full-time compliance consultants.
- **Multilingual support**: Both the interface and norm models are translated, making the platform accessible to non-English-speaking markets.
- **Pay-per-use pricing**: Businesses only pay for what they need, lowering the entry barrier for SMBs.
- **Multi-standard support**: Businesses can work toward several certifications in one place, increasing value per customer and enabling upselling within the same subscription.
- **Simple norm model**: The model of the extracted norms is clear enough for both LLM quick access and understanding and human-readable for the reviewers to quickly move and change its contents.
- **Evidence verification workflow**: Confidence scores, per-criterion explanations, in depth explanation chats and practicioner overrides creates a guided and understandable process for the practicioners. Storing evidence makes this process show the compliance history for the business, which is valuable for demonstrating continuous compliance over time.

#### Weaknesses:
- **Team is not an expert in norms**: The members of the team do not have previous experience with norms and their implementation, which hinders the ability to undestand the quality of results.
- **No active specialist reviewers yet**: The norm model quality control layer exists by design but isn't staffed. Until this is solved, the platform can't safely go live at scale.
- **New standards tied to specialist availability**: To properly release a new standard, there must be specialists available for review.
- **AI hallucination risk**: Even with overrides available, non-expert practitioners may not always recognize when the AI is wrong, which is a serious concern in a compliance context.
- **No formal certification**: The platform explicitly can't certify businesses, which means customers still need external auditors outside the system.
- **Dependency on practitioner judgment**: Evidence-related tasks (mainly overriding the system) rely on the practitioner having some baseline understanding of what good compliance looks like, which isn't guaranteed.
- **Evidence storage liability**: Retaining sensitive business documents long-term makes the platform a big target and creates massive data responsibility obligations.
- **Limited norm extractiom output**: The norm extraction API relies on a free API that provides models more powerful that what its feasible to run locally, but has harsh limits which severly limits the capacity for continuous extractions.

#### Opportunities:
- **Audit firm partnerships**: Partnering with certified auditors could close the certification gap, creating a full pipeline from preparation to formal audit, and lending credibility to the platform.
- **Continuous norm updates**: Being the platform that keeps norm models most current and accurate (with specialist-reviewed updates) is a strong long-term differentiator.
- **Multilingual as a market advantage**: Most competitors are English-first. Targeting non-English-speaking SMB markets in Europe, Latin America, or Asia could be a strong go-to-market wedge.
- **Vertical expansion**: The system is designed for portability to other standards, allowing for future expansions to new frameworks.

#### Threats:
- **Liability exposure**: If a business follows the platform's guidance and fails an audit, there's potential reputational or even legal risk depending on how the platform's advice is framed.
- **Larger incumbents adding AI**: Vanta, Drata and similar GRC platforms are already established and have the resources to add similar AI features to cater to the same market, but with more resources.
- **Trust barrier**: Small businesses in security-sensitive contexts may be hesitant to upload internal evidence and sensitive documents to any third-party platform, even with a local LLM.
- **Norm copyright issues**: Many ISO and similar standards are copyrighted documents. Processing them through an LLM and storing structured derivatives could raise legal questions depending on jurisdiction and licensing terms.
- **Transition from academic to commercial**: The transition from an academic project into a production-grade, legally sound, commercially trusted platform is substantial and may bring up many additional technicalities.

### 6.3. PESTLE Analysis

#### Political

**Government incentives for digital innovation**  
Portugal's participation in the EU-funded **Portugal 2030** programme and the **Plano de Recuperação e Resiliência (PRR)** includes explicit incentives for digital transformation and AI adoption in businesses. CertiBot, as an AI-driven tool supporting regulatory compliance, is positioned to benefit from grants or co-financing schemes aimed at SMEs undergoing digital modernisation.

**Regulatory pressure driving demand**  
The EU's **NIS2 Directive** (Directive (EU) 2022/2555), which came into force in 2024, significantly expands the scope of organizations required to implement cybersecurity frameworks (including ISO 27001-aligned controls). This creates a direct political driver for CertiBot's target market, because organizations that were previously outside mandatory compliance scope are now legally required to act.

**Digital Single Market policies**  
EU policy increasingly pushes for harmonised compliance standards across member states. This is favourable for CertiBot's scalability: a tool that works for Portuguese organizations can be extended across the EU without significant regulatory re-engineering.

**Risk: political instability and policy reversals**  
Funding programmes like Portugal 2030 are subject to political cycles. A change in government priorities or EU budget reallocations could reduce available incentives for digital innovation projects.

---

#### Economic

**Infrastructure costs tied to foreign currency**  
The **Google Gemini API**, used for norms extraction, is priced in US dollars, meaning EUR/USD exchange rate fluctuations have some impact on operational costs. However, since extraction only occurs when new standards are ingested, this is not a significant ongoing concern.

**Hardware costs for running local LLMs**  
CertiBot runs day-to-day queries via **Ollama** on its own infrastructure, avoiding per-query cloud costs. However, this shifts the cost to hardware, as running LLMs continuously requires machines with significant computational capacity (GPU/CPU). As the number of users grows, scaling this infrastructure represents a meaningful operational cost on CertiBot's side.

**Compliance as non-discretionary spending**  
Compliance is not optional for organizations subject to ISO or GDPR requirements. This makes CertiBot's target market relatively **price-inelastic**. Organizations face regulatory fines and audit failures if they do not maintain compliance, creating a strong economic case for adoption even during periods of budget pressure.

**Cost advantage over traditional consulting**  
ISO 27001 certification typically requires expensive external consultants (costs ranging from €10,000 to €50,000 depending on organization size). CertiBot offers a significantly cheaper alternative for internal preparation.

---

#### Social

**Digitally literate target audience**  
CertiBot's primary users are professional, digitally literate users, so there is no significant digital literacy barrier to adoption.

**Growing organisational pressure to demonstrate compliance**  
Stakeholders (clients, investors, and partners) increasingly require demonstrated compliance certifications before entering business relationships. Beyond regulatory obligation, compliance has become a matter of **trust**. Organizations that can demonstrate adherence to recognised standards (such as ISO 27001) signal reliability and security to their clients, which is increasingly a competitive differentiator. This social and commercial pressure accelerates adoption of tools that help organisations prepare for audits.

**Resistance to AI in high-stakes professional contexts**  
A meaningful adoption risk is the cultural resistance among compliance professionals to delegating regulatory judgment to an AI system. Experienced compliance officers may distrust AI-generated assessments, particularly when the consequences of errors are regulatory penalties. CertiBot must position itself clearly as a **support tool**, not a replacement for professional judgment (which is already reflected in its terms and conditions).

**"AI replacing jobs" perception**  
Compliance consultants and internal compliance teams may perceive CertiBot as a threat to their role. This is a reputational and adoption risk, particularly in organisations where compliance is handled by a dedicated team rather than automated tooling.

---

#### Technological

**Rapid evolution of LLMs (opportunity and risk)**  
CertiBot's core value is built on generative AI. This is both an opportunity and a risk: improvements in LLM capabilities (reasoning, accuracy, context length) directly improve CertiBot's outputs without requiring major platform changes. However, the rapid pace of change also means that current model integrations may become outdated quickly, requiring ongoing maintenance to keep up with the state of the art.

**Dependency on Google Gemini**  
The norms extraction pipeline relies heavily on **Google Gemini**. A pricing change, API deprecation, or service disruption from Google would have a direct impact on CertiBot's functionality. This single-vendor dependency is a technological risk that could be mitigated over time by supporting alternative LLM backends.

**Ollama and local inference maturity**  
**Ollama** has seen rapid adoption and has a large, active community, making it a reliable choice for local LLM inference. The open-source models it supports are evolving quickly, which means CertiBot can benefit from model improvements without changing its infrastructure. The main consideration is keeping up with model updates to ensure response quality remains high.

**Low barrier to competition**  
The accessibility of LLM APIs means a competitor could build a functionally similar compliance assistant in a short timeframe. CertiBot's defensible value lies in its **validated normative knowledge base** (curated by compliance specialists) and its domain-specific architecture, not the AI layer alone.

**Emerging AI agents could extend the platform**  
Advances in autonomous AI agents (tool use, multi-step reasoning) could allow CertiBot to move beyond passive Q&A and assessment into **active compliance workflow automation**, by automatically identifying gaps, generating remediation plans, and tracking progress. This is a significant future opportunity.

**Stable underlying stack**  
The core infrastructure (FastAPI, React, PostgreSQL, MongoDB, Keycloak, Docker) relies on mature, widely-adopted technologies with long-term community support. This reduces the risk of foundational instability.

#### Legal

**EU Artificial Intelligence Act (risk classification)**  
The **EU AI Act** (Regulation (EU) 2024/1689), now in force, classifies AI systems by risk level. CertiBot operates as a decision-support tool in a professional compliance context. While it does not make autonomous decisions, its outputs (compliance scores, gap analyses) influence organizational actions. Future regulatory guidance may clarify whether such tools fall under **high-risk** AI categories, which would impose additional transparency, documentation, and conformity assessment obligations.

**AI Liability Directive (proposed)**  
The proposed **EU AI Liability Directive** would make it easier for users to seek compensation for damages caused by AI systems. If adopted in its current form, it could shift the burden of proof in disputes involving AI-generated compliance assessments, increasing the legal exposure of CertiBot's developers and reinforcing the importance of the liability disclaimers already defined in the Terms and Conditions.

**GDPR enforcement tightening**  
GDPR enforcement by national supervisory authorities (including Portugal's **CNPD**) is intensifying. Future interpretations or amendments may impose stricter requirements on how AI systems process personal data, including data embedded in compliance documents. CertiBot must monitor these developments to ensure ongoing compliance.

**NIS2 and expanding ISO 27001 demand**  
The NIS2 Directive expands mandatory cybersecurity requirements to a wider set of sectors and organizations. As more organizations become legally required to implement ISO 27001-aligned controls, the addressable market for CertiBot grows. Future revisions to NIS2 or related directives could further expand this demand.

**ISO standard updates**  
Normative standards like ISO 27001 are periodically revised. When a new version is released, CertiBot's entire knowledge base for that standard must be re-extracted and re-validated. This is an operational and legal risk: using outdated normative criteria in compliance assessments could expose the platform to liability and reputational damage.

**Digital Services Act**
The **Digital Services Act** (Regulation (EU) 2022/2065) introduces new obligations for digital platforms operating in the EU, particularly around transparency. Future extensions of its scope could impose additional requirements.

#### Environmental

**LLM inference has significant energy consumption**  
Running large language models, both via the Google Gemini API and locally via Ollama, is computationally intensive and energy-heavy. For organizations with carbon neutrality goals or ESG reporting requirements, the environmental cost of AI-assisted compliance tooling may be a consideration.

**Google's sustainability commitments**  
Google has committed to operating on carbon-free energy by 2030. Using the Gemini API means CertiBot's cloud inference workloads fall under Google's sustainability umbrella, which is a positive factor for organizations evaluating their own digital carbon footprint.

**Opportunity: optimising for efficiency**  
CertiBot can reduce its environmental footprint through technical optimisations: caching repeated LLM responses, using lighter models for lower-complexity tasks, and minimising redundant API calls. These optimisations simultaneously reduce costs and carbon impact.

**Emerging digital sustainability regulation**  
The EU's **Green Deal** and evolving digital sustainability policies may eventually require platforms to report on the energy consumption of AI systems. CertiBot should anticipate this as a future compliance requirement for the platform itself.
